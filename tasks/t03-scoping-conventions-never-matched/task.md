When Sokrates creates a configuration (`init`), it classifies the files of a codebase with a built-in list of default scoping conventions: path and content patterns that put files into the test, generated, build-and-deployment, other or ignored scope. Four of these default conventions can never match any file because of typos in their patterns, so the files they are meant for silently stay in the main scope and are counted as production code:

1. the three rules that recognize generated HTML pages — a page generated by pkgdown (a line containing "Generated by pkgdown: do not edit by hand" within the first 2 lines), by Doxygen ("Generated by Doxygen" within the first 31 lines), or by any tool that writes a `<meta name="generator" …>` tag (within the first 31 lines) — recognize `.html` and `.xhtml` files but not `.htm` files, although `.htm` was meant to be covered;
2. the generated-code rule for .NET assembly documentation files (an XML file with a `<doc>` line within its first 2 lines) and the rule for JavaScript files starting with `// Generated by …` only match a file literally named `.xml` / `.js`, never a real `MyAssembly.xml` or `app.js`;
3. the build-and-deployment rule for Gradle JavaScript scripts matches only a file literally named `.-gradle.js` instead of any `*-gradle.js` file.

Fix these default conventions so that they match the files they are meant for: a pkgdown/Doxygen/meta-generator `.htm` page and a `<doc>` XML file land in the generated scope, a `build-gradle.js` in the build-and-deployment scope. Everything the conventions matched before must still match (a Doxygen `.html` page, a `.xhtml` page with a generator meta tag, a `build.gradle`), and ordinary hand-written `.htm`, `.js` and `.xml` files must stay out of those scopes.
